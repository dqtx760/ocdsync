让 Codex 越用越强，让 Codex 自动进化！

让 Codex 能够持续修正自己，带你搭建一套四层自进化系统，让你的 Codex 完全超越别人！

自进化系统要解决的，就是把零散的纠正经验和约束，变成下一次还能自动生效的工程资产。
最稳的方式不是堆功能，而是先搭四层认知核心路径：

第一层：认知核心
作用是把系统的方向写清楚，让 Codex 每次进入项目时，都先知道自己服务什么目标。
这层最直接的落点是 AGENTS.md，里面放原则、边界、完成标准、思考顺序。

第二层：路径作用域规则
不同目录、不同任务、不同风险等级，应该触发不同的约束，而不是一把尺子量所有场景。
在 Codex 里，这层可以落到 Rule Hooks/Skills 上，让某些规范只在某些路径生效。

第三层：专用 Subagent 分工
把规划、验证、审查、采集拆给不同的 Subagent，让每个角色只在自己的边界内积累经验。
这样做的好处是上下文干净、职责清楚，后面要升级某个角色时，也不用把整套系统一起重做。

第四层：记忆与进化循环
你纠正 Codex 一次之后，这条经验到底怎么活到下一次？
只有被写进文件、被定期复盘，才会开始真正积累。
把 corrections / observations / learned_rules / evolution_log 这几类信息组织成闭环。

同时也不是每个人都需要给 Codex 上这套自进化系统，关键看你是不是已经进入了重复纠错和长期协作阶段。
如果只是偶尔写点小脚本，默认状态已经够用。

但如果你已经开始长期跑项目、多人协作、反复复盘，这套方法就很值钱。

最小可用版本
如果你想先跑起来，不要上来就搭完整系统。最小版本只需要 5 个文件：
- AGENTS.md
- memory/corrections.md
- memory/observations.md
- memory/learned_rules.md
- memory/evolution_log.md

然后每次任务结束时，让 Codex 固定问自己： 
本次任务是否产生了可复用经验？

如果有：
1. 用户是否纠正过我？
2. 是否发现了新的项目事实？
3. 是否应该升级为长期规则？
4. 是否要写入 evolution_log？

我的建议是：你先搭一个「轻量但完整」的版本，不急着做自动化。等你连续使用几轮之后，再把高频规则升级成 Skills，这样你就会发现你的 Codex 越来越好用了！
